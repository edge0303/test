# 정부지원금 레이더

중소기업·소상공인을 위한 **정부지원금·정책자금 일정 레이더 + 지원서 제작** 웹 애플리케이션입니다.
[기획서](./gov-support-platform-plan.md)에서 확정한 12개 의사결정을 그대로 구현했습니다.

```
사업자번호 입력 → 3단계 자격 판정 → D-day 대시보드 → PSST 초안 생성
   → 심사위원 채점 → 자동 재작성 루프 → 팩트체크 → 전문가 검수 요청
```

---

## 빠른 시작

```bash
npm install
cp .env.example .env      # 키가 없어도 전부 동작합니다
npm run seed              # 샘플 공고 28건 적재
npm run dev               # http://localhost:3000
```

브라우저에서 사업자등록번호를 넣으면 온보딩이 시작됩니다.
테스트용 유효 번호: `220-81-62517` (체크섬을 통과하는 번호면 무엇이든 됩니다)

## 키가 없어도 전부 동작합니다

이 앱은 **외부 키가 하나도 없어도 처음부터 끝까지 동작**하도록 만들었습니다.
데모·오프라인에서 흐름이 끊기면 안 되고, 외부 장애가 서비스 중단으로 이어지면 안 되기 때문입니다.

| 환경변수 | 없을 때 | 있을 때 |
| --- | --- | --- |
| `BIZINFO_API_KEY` | 샘플 공고 28건으로 동작 (UI에 '샘플 데이터' 배지) | 기업마당 실공고 수집 |
| `NTS_API_KEY` | 사업자번호 **체크섬 검증**만 수행 | 휴·폐업 상태와 과세유형 자동 확인 |
| `ANTHROPIC_API_KEY` | **결정적 템플릿 모드** — 초안·재작성 모두 규칙 기반 | AI가 초안·재작성·총평 작성 (채점은 항상 결정적) |

## 구현된 것 / 아직 아닌 것

### 구현됨

- **사업자번호 검증** — 국세청 체크섬 알고리즘, 개인/법인 구분
- **하이브리드 온보딩** — 자동 확인 항목과 질문 항목을 분리해 제시
- **공고 수집** — 시드 적재 + 기업마당 API 수집(멱등 upsert)
- **3단계 매칭 엔진** — 결정적 룰 평가, 구간 기반 판정, 5요소 적합도 점수
- **판정 근거 노출** — 요건 원문 ↔ 우리 회사 값을 나란히 표시
- **D-day 대시보드** — KPI, 액션카드, 월간 캘린더, 3그룹 아코디언, 마감 알림 예정
- **PSST 초안 생성** — 팩트 슬롯 기반, 숫자를 지어내지 않음
- **심사위원 채점** — 16개 결정적 체크 + 미확인 항목 감점
- **자동 재작성 루프** — 실패한 체크만 섹션 단위로 보강, 3중 종료 조건
- **팩트체크** — 모든 수치를 프로파일과 전수 대조
- **편집 후 즉시 재채점**, **마크다운 내보내기**
- **전문가 검수 요청 + 내부 검수 큐** — 자동 사전정리 메모 포함

로그인·결제 · 카카오 알림톡 발송 · 구글 캘린더 연동 · HWP/PDF 첨부 파싱 ·

## 설계에서 타협하지 않은 3가지

### 1. 매칭은 LLM을 쓰지 않는다

`src/lib/rules.ts`, `src/lib/matcher.ts` 는 순수 규칙 엔진입니다.
"왜 이 공고가 떴는지"를 공고 원문과 함께 설명할 수 없으면 신뢰가 무너지고,
규제 관점에서도 위험하기 때문입니다. LLM은 지원서 **생성**에만 씁니다.

### 2. 애매하면 '불가'가 아니라 '확인필요'

온보딩에서 매출·근로자수를 **구간**으로 받습니다. 대표님들이 정확한 값을 몰라
이탈하는 것이 가장 큰 손실이기 때문입니다. 대신 판정은 구간 전체가 요건을
만족할 때만 통과, 전체가 위배할 때만 불가, **걸쳐 있으면 확인필요**입니다.

```
매출 구간 5~10억, 요건 "7억 이하"  →  걸침  →  ⚠ 확인필요
```

첨부 파싱이 불완전한 공고(`parse_status != 'parsed'`)도 자동으로 확인필요로 내립니다.
놓친 공고 1건이 서비스 전체 신뢰를 무너뜨리기 때문입니다.

### 3. 숫자를 지어내지 않는다

초안 생성기는 숫자를 직접 쓸 수 없고 `{{fact:key}}` 슬롯만 사용합니다.
값이 없으면 문장을 만들지 않고 `[확인 필요: 라벨]` 마커를 남깁니다.

- 화면에서는 **노란 하이라이트**로 표시
- Verifier가 최종 산출물의 모든 수치를 프로파일과 전수 대조
- 미확인 항목이 남으면 **채점에서 감점** — 형식만 갖춘 빈 계획서에 만점을 줄 수 없습니다
- 검수 요청 시 미확인 항목이 검수자 메모 최상단에 자동으로 정리됩니다

## 구조

```
src/
  lib/
    bizno.ts       사업자번호 체크섬 검증
    nts.ts         국세청 상태조회 (선택)
    profile.ts     구간 정의, 완성도 계산
    db.ts          SQLite 스키마
    repo.ts        질의 계층
    ingest.ts      시드 + 기업마당 수집 (API 매핑은 여기 한 곳)
    rules.ts       결정적 룰 평가기 (PASS/FAIL/UNKNOWN)
    matcher.ts     3단계 판정 + 적합도 점수
    psst.ts        PSST 템플릿 + 팩트 슬롯
    judge.ts       심사위원 채점 (16개 체크 + 미확인 감점)
    rewriter.ts    결함별 보강 블록
    verifier.ts    수치 전수 대조
    llm.ts         Anthropic 클라이언트 (선택)
    pipeline.ts    작성→채점→재작성→검증 오케스트레이션
  app/
    onboard/       온보딩
    dashboard/     D-day 대시보드
    application/   지원서 편집 + 채점 패널
    admin/reviews/ 내부 검수 큐
    api/           라우트 핸들러
```

### 재작성 루프 종료 조건

1. 목표점(85) 도달
2. 3회 도달
3. 상승폭 2점 미만 (수렴)
4. 고칠 수 있는 결함이 남아 있지 않음 — 남은 감점이 '미확인 항목'뿐이면
   그것은 사용자가 실제 값을 채워야 하는 몫입니다

## 실데이터 연결

```bash
# .env
BIZINFO_API_KEY=발급받은_인증키
npm run ingest
```

목록 API는 자격요건 **원문을 주지 않습니다.** 따라서 수집된 공고는 전부
`parse_status = 'partial'` 로 적재되어 **확인필요**로 분류됩니다.
지원대상 요약문에서 확실하게 뽑아낼 수 있는 요건(업력·근로자수·여성기업)만
`deriveRulesFromTarget()` 이 추출합니다. 확신이 없으면 룰을 만들지 않습니다.

API 응답 형태가 바뀌면 `npm run ingest` 가 **조용히 실패하지 않고** 응답 샘플을
출력합니다. `src/lib/ingest.ts` 의 `mapBizinfoItem()` 한 곳만 고치면 됩니다.

## 데이터에 대한 고지

`data/seed-programs.json` 은 실제 공고를 재현한 것이 아니라 매칭 동작을 검증하기 위한
**샘플 데이터**입니다. 실제 공고 정보는 반드시 원문을 확인하십시오.
자동 생성된 지원서는 **초안**이며, 최종 작성 및 제출 책임은 신청 기업에 있습니다.
